# Техническое задание: конструктор frontend для AI-сервисов

## 1. Назначение проекта

Необходимо разработать веб-конструктор frontend для сборки, настройки и предварительного расчёта AI-сервисов.

Конструктор должен позволять пользователю:

- выбрать тип AI-продукта; (с backend получает enum с типами)
- выбрать необходимые каналы общения и публикации; (статичны)
- добавить сотрудников и права доступа; (админ или обычный)
- рассчитать стоимость запуска и ежемесячного обслуживания;
- отдельно учитывать расходы на использование AI;
- сформировать итоговую конфигурацию заказа;
- передать заявку менеджеру или получить коммерческое предложение. (Разрешается использовать заслонку)

Все цены, названия компаний, внутренние расходы, персональные данные, реальные ссылки, контактные данные и сведения о себестоимости должны храниться вне публичного интерфейса либо заменяться обезличенными настройками.

---

## 2. Область применения

Конструктор предназначен для подбора и конфигурации готовых AI-решений, например:

- образовательный AI-помощник;
- AI-методист;
- AI-помощник для создания контента;
- AI-SMM-ассистент;
- корпоративный помощник;
- AI-агент для работы с документами;
- комбинированный комплект из нескольких AI-агентов.

Система должна поддерживать как типовые решения, так и передачу нестандартных заказов на индивидуальную оценку.

---

## 3. Основные пользовательские сценарии

### 3.1. Подбор продукта

Пользователь открывает конструктор и выбирает один из вариантов:

- один AI-агент;
- комплект из двух AI-агентов или больше;
- индивидуальное решение;
- консультация по подбору.

После выбора отображается краткое описание продукта, его назначение и базовая стоимость запуска.

### 3.2. Настройка AI-агента

Пользователь указывает:

- назначение агента;
- необходимые функции;
- количество сотрудников;
- используемые каналы;
- каналы публикации;
- необходимость работы с файлами и базой знаний;
- дополнительные ограничения.

### 3.3. Выбор интеграций

Пользователь выбирает нужные подключения из каталога:

- мессенджеры; 
- социальные сети;
- электронная почта;
- публикационные каналы;
- внешние сервисы;
- индивидуальные интеграции.

Для каждой интеграции необходимо отображать: (с backend получает +)

- название; +
- краткое назначение; +
- уровень сложности;
- стоимость подключения; +
- возможные ограничения; +
- необходимость предоставления доступа; +
- наличие готового коннектора.

### 3.4. Расчёт стоимости

Конструктор автоматически рассчитывает:

- стоимость запуска;
- стоимость интеграций;
- стоимость ежемесячного обслуживания;
- стоимость дополнительных сотрудников;
- стоимость дополнительного хранения;
- ориентировочный бюджет AI;
- итоговую сумму за первый период.

### 3.5. Передача заявки

После завершения настройки пользователь может:

- оставить заявку;
- скачать или получить коммерческое предложение;
- отправить конфигурацию менеджеру;
- вернуться к редактированию параметров.

Перед отправкой заявки система должна показать итоговую конфигурацию и предупредить о возможных индивидуальных работах.

## 4. Структура интерфейса

### 4.1. Главная страница

Главная страница должна содержать:

- заголовок и краткое описание конструктора;
- блок выбора продукта;
- преимущества использования конструктора;
- примеры готовых конфигураций;
- кнопку перехода к настройке;
- блок с пояснением модели оплаты;
- FAQ;
- дисклеймер о предварительном характере расчёта.

### 4.2. Экран конструктора

####  Тип решения

- название;
- описание;
- список основных возможностей;
- базовая стоимость;
- кнопка выбора.

#### Функциональность

- генерация текста;
- подготовка планов и заданий;
- создание контент-плана;
- работа с базой знаний;
- ответы на обращения;
- поиск по документам;
- публикация материалов;
- анализ входящих сообщений;
- работа с несколькими сотрудниками;
- индивидуальные сценарии.

Некоторые функции могут быть недоступны для выбранного продукта. (с backend приходит struct с разрешениями)

#### Публикация контента

- канал публикации;
- тип публикуемого содержимого;
- необходимость публикации текста;
- необходимость публикации готовых изображений;
- необходимость работы с комментариями;
- необходимость сбора статистики.

Если выбран расширенный сценарий, система должна отметить его как услугу повышенной сложности.

#### Сотрудники и доступы

- количество сотрудников;
- количество администраторов;
- необходимость личной истории;
- необходимость индивидуальной базы знаний;
- доступ к общей базе компании;
- ограничения для отдельных сотрудников.

Первый администратор включается в базовую стоимость. Дополнительные сотрудники рассчитываются отдельно.

#### Хранилище и база знаний

- использование базы знаний;
- объём загружаемых данных;
- количество файлов;
- необходимость ручной подготовки документов;
- необходимость распознавания больших архивов;
- дополнительный объём хранения.

Следует разделить:

- самостоятельную загрузку материалов;
- ручную обработку материалов;
- нестандартный импорт;
- обработку больших архивов.


#### Шаг 7. AI-бюджет

- собственный API-ключ или поддерживаемый аккаунт;
- отдельный баланс AI;
- уточнить способ оплаты позже.

Необходимо отображать предупреждение, что расход AI зависит от:

- количества запросов;
- размера документов;
- количества поисковых операций;
- генерации изображений;
- голосовых функций;
- использования внешних инструментов.

Фиксированный безлимитный расход AI не должен заявляться по умолчанию.

## 5. Логика расчёта

Все тарифы должны задаваться через конфигурацию, а не быть жёстко зашиты в компоненты интерфейса.

### 5.1. Стоимость запуска

Общая формула:

Стоимость запуска = Стоимость продукта + Стоимость интеграций + Стоимость дополнительных модулей

Интеграции разделяются на три уровня:

- базовый;
- стандартный;
- расширенный.

Стоимость каждого уровня должна настраиваться в административной конфигурации.

### 5.2. Ежемесячная стоимость

Общая формула:

Ежемесячная стоимость = Базовое обслуживание + Дополнительные сотрудники + Дополнительное хранение + Сопровождение интеграций

При выборе нескольких AI-агентов может применяться отдельный пакетный тариф.

### 5.3. Дополнительные сотрудники

Правила:

- один администратор включён в базовый тариф;
- каждый дополнительный сотрудник оплачивается отдельно;
- сотрудник с доступом к нескольким агентам одной организации считается одним местом;
- посетители и внешние пользователи не считаются сотрудниками, если они не имеют отдельного рабочего пространства;
- отключение сотрудника влияет на следующий расчётный период.

### 5.4. Интеграции

Каждая точка подключения считается отдельной интеграцией.

Примеры:

- разные каналы — разные подключения;
- разные почтовые ящики — разные подключения;
- приём и отправка сообщений в одном модуле — одна интеграция;
- публикация текста и готового изображения в одном канале — одна интеграция;
- сложная автоматизация между несколькими сервисами — индивидуальная разработка.

### 5.5. Ограничение автоматического расчёта

Если пользователь выбирает большое количество интеграций, конструктор должен прекратить точный автоматический расчёт и показать сообщение:

> Для данной конфигурации требуется индивидуальная оценка. Оставьте заявку, чтобы получить расчёт стоимости и сроков.

Порог перехода в индивидуальный расчёт должен задаваться в настройках.

## 6. Категории услуг

### 6.1. Стандартные услуги

К стандартным услугам относятся:

- настройка готового AI-агента;
- подключение готового коннектора;
- добавление подготовленных текстовых материалов;
- настройка стандартных ролей;
- проверка на согласованных примерах;
- базовая инструкция;
- ограниченное количество раундов правок.

### 6.2. Индивидуальные услуги

В отдельную оценку переводятся:

- разработка нестандартной логики;
- создание нового коннектора;
- интеграция с нестандартной CRM;
- отдельная авторизация;
- обработка больших архивов;
- ручная подготовка документов;
- генерация видео;
- создание сложных сценариев;
- голосовые звонки;
- работа с телефонией;
- автоматизация цепочек между несколькими системами;
- крупное количество одинаковых подключений.

В интерфейсе такие функции должны иметь метку:

> Индивидуальный расчёт

## 10. Требования к frontend

### 10.1. Общие требования

Frontend должен быть:

- адаптивным;
- доступным с компьютера; (остальные идут в плюс)
- совместимым с современными браузерами;
- устойчивым к обновлению страницы;
- пригодным для локализации;
- подготовленным к подключению backend API.

### 10.2. Состояние конструктора

Состояние конфигурации должно:

- восстанавливаться после обновления страницы;
- пересчитываться при каждом изменении параметров;
- корректно обрабатывать удаление выбранных элементов.

### 10.3. UX-требования

Необходимо обеспечить:

- отображение текущей стоимости;
- краткие подсказки;
- раскрывающиеся подробности;
- заметное обозначение индивидуальных услуг;
- отсутствие неожиданных изменений итоговой суммы;
- подтверждение перед сбросом конфигурации;

## 11. Технический стек

Стек может быть выбран командой разработки, но рекомендуется:

- React;
- TypeScript;
- Vite;
- компонентная UI-библиотека;
- CSS Modules, Tailwind CSS или .

Архитектура должна разделять:

- UI-компоненты;
- бизнес-логику расчёта;
- типы данных;
- конфигурацию тарифов;
- API-клиент;
- валидацию;
- состояние конструктора.

Расчёт стоимости не должен находиться непосредственно внутри JSX-компонентов.

## 12. Модель данных

Пример базовых сущностей:

```ts
type Product = {
  id: string;
  title: string;
  description: string;
  basePrice: number;
  monthlyPrice: number;
  availableFeatures: string[];
  availableIntegrations: string[];
};

type Feature = {
  id: string;
  title: string;
  description: string;
  price: number;
  monthlyPrice?: number;
  requiresIndividualEstimate?: boolean;
};

type Integration = {
  id: string;
  title: string;
  category: 'communication' | 'publishing' | 'email' | 'custom';
  level: 1 | 2 | 3 | 'individual';
  setupPrice?: number;
  monthlyPrice?: number;
  description: string;
  requirements?: string[];
  available: boolean;
  requiresIndividualEstimate: boolean;
};

type ConstructorState = {
  productId: string | null;
  featureIds: string[];
  integrationIds: string[];
  employeeCount: number;
  storageGb: number;
  aiPaymentMode: 'own-account' | 'shared-balance' | 'later';
  customRequirements: string;
};

type PriceResult = {
  setupPrice: number | null;
  monthlyPrice: number | null;
  aiBudgetEstimate: number | null;
  requiresIndividualEstimate: boolean;
  warnings: string[];
};
```

## 14. Аналитика

Необходимо предусмотреть события:

- открытие конструктора;
- выбор продукта;
- переход между шагами;
- добавление интеграции;
- удаление интеграции;
- переход к индивидуальному расчёту;
- начало заполнения формы;
- отправка заявки;
- ошибка валидации;
- сброс конфигурации;
- скачивание коммерческого предложения.

В аналитике нельзя передавать:

- персональные данные;
- текст приватных требований;
- API-ключи;
- токены;
- содержимое загруженных документов;
- конфиденциальные сведения клиента.

---

## 16. Критерии приёмки

Проект считается выполненным, если:

- пользователь может пройти весь сценарий настройки;
- стоимость корректно пересчитывается при изменении параметров;
- выбранные настройки сохраняются;
- несовместимые параметры блокируются или сопровождаются предупреждением;
- индивидуальные услуги явно выделяются;
- итоговая конфигурация отображается до отправки заявки;
- форма заявки валидируется;
- заявка отправляется в backend или демонстрационный mock API;
- обновление страницы не приводит к потере черновика;
- в frontend отсутствуют реальные конфиденциальные данные;
- тарифы и интеграции можно изменять через конфигурацию;
